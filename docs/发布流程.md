# DSH 插件发布流程（开发 → GitHub → 1024Store 收录）

> 本 SOP 记录从零把一个 DSH 插件推到线上的完整流程，基于 `@cqpdrcuk/dsh-plugin-npm-advisor` 首发实战整理。
> 流程分四段：① 开发与验证 → ② 打 GitHub topic → ③ 登记 1024Store（PR 收录）→ ④ 发布 npm。

---

## ① 开发与验证（dsh-plugins 内）

在 `packages/` 下新建插件包，目录命名 `tool-<name>`（工具类）。

### 插件必须满足的三件事

1. **是 Cordis 插件**：`src/index.ts` 导出 `name` / `inject` / `apply(ctx)`，用 `ctx.tools.register(defineTool(...))` 注册工具
2. **声明 `dsh.bundle`**（DSH bundle 规范，收录校验必需）——`package.json`：
   ```json
   {
     "main": "src/index.ts",
     "types": "src/index.ts",
     "files": ["src", "cordis.patch.yml"],
     "dsh": { "bundle": { "patch": "./cordis.patch.yml" } },
     "peerDependencies": {
       "@deepseek-ai/cordis": ">=4.0.1",
       "@deepseek-ai/dsh-tools": ">=0.1.0-rc.0"
     },
     "devDependencies": {
       "@deepseek-ai/cordis": "4.0.1",
       "@deepseek-ai/dsh-tools": "0.1.0-rc.8"
     }
   }
   ```
3. **`cordis.patch.yml`**（bundle patch，插件行按包名引用，Node 才能解析已安装代码）：
   ```yaml
   - insert:
       - id: <plugin-id>
         name: '@cqpdrcuk/<包名>'
   ```

### 三档验证（从逻辑到加载，不依赖 DSH 宿主 / LLM key）

| 档 | 命令 | 验证什么 |
|----|------|---------|
| 逻辑冒烟 | `pnpm smoke` | `execute` 核心逻辑（fetch registry / audit 输出 / mermaid 依赖树） |
| Cordis 加载 | `pnpm load-test` | 插件作为 Cordis 插件真实加载：`apply` 执行 + `ctx.tools.register` 注册成功（mock `tools` 服务） |
| 端到端 | `pnpm dsh web --patch dev/cordis.yml` | DSH UI 里 agent 真正调用工具（需 dsh CLI + 模型 key，本机未做） |

根目录 `package.json` 已配好 scripts：
```json
"smoke": "tsx packages/<包>/scripts/smoke.ts",
"load-test": "tsx packages/<包>/scripts/load-test.ts"
```

### 常见坑

- `@deepseek-ai/dsh-tools` 的 **`latest` tag 指向老版本**（依赖未发布的 `dsh-type-meta`，装不上）；devDependencies 必须锁 `0.1.0-rc.8`（`next` tag），不能写 `latest`
- pnpm 11 构建脚本白名单：`pnpm-workspace.yaml` 配 `allowBuilds: { esbuild: true }`（tsx 依赖 esbuild postinstall）
- 插件包目录要有自己的 `README.md`，否则 npm 页面空白

## ② 打 GitHub topic

仓库出现在 `github.com/topics/dsh-plugin` 等页面（无审核，立即生效）。用 `gh`（已装 `C:\Program Files\GitHub CLI\gh.exe`，走环境变量 `GITHUB_TOKEN`）：

```powershell
& "C:\Program Files\GitHub CLI\gh.exe" repo edit ERVeepp/dsh-plugins `
  --add-topic dsh-plugin --add-topic deepseek-harness --add-topic dsh `
  --add-topic cordis --add-topic cordis-plugin
```

验证：
```powershell
& "C:\Program Files\GitHub CLI\gh.exe" repo view ERVeepp/dsh-plugins `
  --json nameWithOwner,url,repositoryTopics -q '{repo: .nameWithOwner, url: .url, topics: [.repositoryTopics[].name]}'
```

> 附带收益：1024Store 每 30 分钟用 `dsh-plugin` topic 增量扫描自动收集仓库（但只有声明了 `dsh.bundle.patch` 才通过校验进目录）。

## ③ 登记 1024Store（PR 收录）

收录方式：向 `imsai-sh/awesome-deepseek-harness-plugins` **发 PR 新增一个 JSON 文件**（不是提 issue）。

### 3.1 fork + clone（首次）

```powershell
cd c:\www\temp
& "C:\Program Files\GitHub CLI\gh.exe" repo fork imsai-sh/awesome-deepseek-harness-plugins --clone --default-branch-only
cd awesome-deepseek-harness-plugins
git checkout -b add-<plugin-name>
```

### 3.2 生成目录条目 JSON

id 规则：`owner/repository/packages/<子包>`（monorepo 子包）；文件名 = 每段转小写、非字母数字转 `-`、`--` 连接：
`catalog/plugins/erveepp--dsh-plugins--packages--tool-npm-advisor.json`

```json
{
  "$schema": "../schema/plugin.schema.json",
  "id": "ERVeepp/dsh-plugins/packages/tool-npm-advisor",
  "name": "npm-advisor",
  "repository": "https://github.com/ERVeepp/dsh-plugins",
  "category": "tools",
  "description": {
    "en": "...",
    "zh": "..."
  },
  "added": "2026-08-21"
}
```

- 字段必填：`$schema` / `id` / `name` / `repository` / `category` / `description{en,zh}` / `added`（schema 见 `catalog/schema/plugin.schema.json`）
- `category` 从 `catalog/categories.json` 选，工具类用 `tools`
- `repository` 始终是前两段推导的仓库根 URL（子目录路径只在 id 里）

### 3.3 单文件提交 + push + PR

```powershell
git add catalog/plugins/<文件名>.json
git diff --cached --check
git commit -m "catalog: add ERVeepp/dsh-plugins/packages/tool-npm-advisor"
git push -u origin add-<plugin-name>

& "C:\Program Files\GitHub CLI\gh.exe" pr create `
  --repo imsai-sh/awesome-deepseek-harness-plugins `
  --head ERVeepp:add-<plugin-name> `
  --title "catalog: add <插件 ID>" --body-file pr-body.md
```

### 3.4 PR 正文模板（pr-body.md）

```markdown
## 摘要

将 [`<插件 ID>`](https://github.com/ERVeepp/dsh-plugins) 添加到 DeepSeek Harness 插件目录。

## 插件验证

- Manifest：`packages/<子包>/package.json`
- 子目录：`packages/<子包>`（安装为 `github:ERVeepp/dsh-plugins#path:packages/<子包>`）
- Bundle patch：`packages/<子包>/cordis.patch.yml`
- 测试命令：`pnpm typecheck && pnpm smoke && pnpm load-test`（在 dsh-plugins 仓库根）
- 测试结果：`<真实的 smoke/load-test 输出>`

## 目录提交确认

- [x] 本 PR 只新增一个 `catalog/plugins/*.json` 文件，不包含其他改动
- [x] 插件仓库声明了 `dsh.bundle.patch`，并已提交引用的补丁文件
- [x] 作者已经测试插件行为和兼容性
- [x] 插件仓库已添加 `dsh-plugin` topic
- [x] 中英文简介中性且准确
- [x] 我理解检查失败时 PR 会保持打开以便修复；非草稿 PR 通过后会自动合并，合并后由 CI 自动同步到网站目录与 README，且收录不代表对插件行为、安全性或质量的背书
```

### 3.5 提交后的自动流程

1. **static-review**：只读校验（单 JSON 变更、schema 字段、`dsh.bundle.patch` 存在、`dsh-plugin` topic、仓库可读）——bot 在 PR 评论结果
2. **自动合并**：新增类 PR 通过即 squash merge；修改/删除类 PR 需维护者人工审核
3. **自动同步**：合并后 CI 推到 deepseek1024.com 数据库 + 刷新 README，无需人工
4. 失败时 PR 保持打开，按 bot 评论只改 `catalog/plugins/*.json` 修复

## ④ 发布 npm（可选，但推荐）

`dsh.bundle` 声明的包发布后，1024Store 网站会标为 VERIFIED（优先用已发布 npm 包安装）。

```powershell
npm login                      # 账号 cqpdrcuk（scope 必须等于 npm 用户名）
cd c:\www\dsh-plugins\packages\<子包>
npm publish --dry-run          # 检查打包内容（files 含 src + cordis.patch.yml + README 自动带）
npm publish --access public
```

发布前检查：`files` 包含 `src` 和 `cordis.patch.yml`；包目录有自己的 `README.md`；版本号 `version` 已递增。
